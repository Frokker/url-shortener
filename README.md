Принцип разбиения такой: на этапе 1 ты намеренно делаешь счётчик кликов «в лоб» — синхронный инкремент в БД на каждом редиректе. Это плохо для прода, и в этом весь смысл: на этапе 2 у тебя есть конкретная боль, которую ты рефакторишь, и ты физически чувствуешь, почему синхронная запись на горячем пути убивает латентность. Без этого «до/после» урок не закрепляется. Держим только HTTP, без gRPC — ты просил максимально простой.

## Стек

**Этап 1:** Go, chi (роутер), Postgres + pgx/pgxpool, миграции через goose или golang-migrate, конфиг через env в структуру, логирование `slog` (stdlib), Redis как read-through кэш (синхронный — это не конкурентность, просто кэш), тесты на stdlib `testing` + testify + testcontainers-go для интеграционных, Docker Compose (app + postgres + redis).

**Этап 2 добавляет:** Kafka (или NATS) для потока событий кликов, Prometheus-клиент для метрик, и собственно конкурентные примитивы Go — буферизованные каналы, worker pool, `context`, `sync`. Никаких новых внешних зависимостей ради зависимостей.

## Модель данных

`links`: code (PK, короткий), original_url, is_custom, created_at, expires_at (nullable), click_count (денормализованный счётчик). На этапе 1 `click_count` инкрементится синхронно. На этапе 2 заводишь `click_events` (или таблицу агрегатов) и обновляешь счётчики батчами.

## Этап 1 — синхронный скелет

Функционал: создать короткую ссылку (с опциональным кастомным алиасом и TTL), редиректить по коду, отдавать статистику, удалять. Идемпотентность создания: одинаковый URL → тот же код (через unique-констрейнт). Слои строго разделены: handler → service → repository, чтобы service не знал про HTTP, а repository — про бизнес-логику.

Ручки:

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/v1/links` | Создать. Body: `{url, custom_alias?, ttl_seconds?}` → `{code, short_url, expires_at}` |
| GET | `/{code}` | Редирект (301/302) на оригинал; синхронно `+1` к счётчику; проверка TTL |
| GET | `/api/v1/links/{code}` | Метаданные: original_url, clicks, created_at, expires_at |
| DELETE | `/api/v1/links/{code}` | Удалить ссылку |
| GET | `/healthz` | Liveness |
| GET | `/readyz` | Readiness — пингует Postgres и Redis |

Поток редиректа на этапе 1: смотрим Redis → если промах, идём в Postgres и кладём в кэш → инкрементим `click_count` в БД → отдаём редирект. Инкремент синхронный и блокирующий — так и задумано.

Definition of done: чистые слои с интерфейсами на границах, валидация входа, идиоматичные ошибки (`errors.Is/As`, обёртка `%w`), graceful shutdown по сигналу, table-driven юнит-тесты на service и интеграционные на repository через testcontainers, поднимается одной командой через docker-compose.

## Этап 2 — конкурентность

Главный рефактор: убираешь синхронный инкремент с горячего пути. Теперь редирект кидает событие клика в буферизованный канал и **сразу** отвечает; отдельный пул воркеров вычитывает события, копит в батч (по размеру N или по таймеру T — что наступит раньше) и сбрасывает агрегированные счётчики в Postgres одним запросом. Это твой главный конкурентный кусок: каналы, worker pool, батчинг, backpressure и graceful drain.

Что реализуешь:
- **Async click pipeline:** буферизованный канал → worker pool → батчевый флаш в БД. Политика backpressure при заполнении канала (дропать с метрикой / блокировать — обоснуй выбор). На shutdown через `context` аккуратно дренишь остаток батча, ничего не теряя.
- **Kafka-продьюсер:** каждое событие клика асинхронно летит в топик `clicks` для внешней аналитики (fire-and-forget против at-least-once — потрогай оба).
- **Rate limiting:** middleware на token bucket (по IP или API-ключу) на всех ручках.
- **Background expiry sweeper:** горутина на `time.Ticker`, которая периодически чистит протухшие ссылки.
- **Корректность:** прогон `-race` чистый, проброс `context` везде, метрики глубины очереди / размера батча / числа дропов.

Ручки (добавляются к этапу 1):

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/metrics` | Prometheus: латентность по перцентилям, queue depth, batch size, drops |
| GET | `/api/v1/links/{code}/stats` | Расширенная аналитика (агрегаты по времени) из Kafka-конвейера |

Rate limiting — это middleware, отдельной ручки не требует; вешается на весь роутер.

Definition of done: редирект больше не ждёт записи в БД (замерь p99 до и после — это твоя главная цифра на собес), `go test -race` зелёный, на shutdown ни одно событие из канала не теряется, метрики показывают живой queue depth под нагрузкой. Прогони нагрузочный тест (vegeta / k6) и зафиксируй p50/p99 обоих этапов рядом — это и есть доказательство, что ты понял разницу.
