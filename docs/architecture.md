## Принципы

1. **Строгое разделение слоёв.** `handler` знает про HTTP, `service` — про бизнес-правила,
   `repository` — про БД. Зависимости направлены внутрь: handler → service → repository.
   Service ничего не знает про `http.Request`, repository ничего не знает про бизнес-логику.
2. **Интерфейсы на границах.** Service зависит от интерфейса репозитория, а не от конкретной
   реализации на pgx. Это даёт подмену в тестах и развязку.
3. **`context.Context` пробрасывается везде** — от handler до запроса в БД. Дедлайны и отмена
   работают сквозь все слои.
4. **Идиоматичные ошибки.** Доменные ошибки-сентинелы (`ErrNotFound`, `ErrExpired`,
   `ErrAliasTaken`), обёртка через `%w`, разбор через `errors.Is/As`. HTTP-коды выставляет
   только handler, мапя доменные ошибки на статусы.
5. **Этап 1 намеренно наивен.** Синхронный инкремент счётчика — это не баг, это учебная
   точка боли. Не оптимизируем её до Этапа 2.

## Слоистая архитектура

```
┌──────────────────────────────────────────────────────────────┐
│  transport / handler  (internal/transport/http)              │
│  - парсит/валидирует HTTP-запрос                              │
│  - вызывает service                                          │
│  - мапит доменные ошибки → HTTP-коды                         │
│  - НЕ знает про SQL                                          │
└───────────────────────────┬──────────────────────────────────┘
                            │ доменные типы, context
┌───────────────────────────▼──────────────────────────────────┐
│  service  (internal/service)                                 │
│  - бизнес-правила: генерация кода, проверка TTL,             │
│    идемпотентность, валидация алиаса                         │
│  - оркестрирует repository + cache (+ канал кликов на Эт.2)  │
│  - НЕ знает про http.Request и про конкретный драйвер БД     │
└───────────────────────────┬──────────────────────────────────┘
                            │ интерфейсы Repository, Cache
┌───────────────────────────▼──────────────────────────────────┐
│  repository  (internal/repository/postgres, .../redis)       │
│  - SQL через pgxpool, маппинг строк в доменные структуры     │
│  - НЕ содержит бизнес-логики                                 │
└──────────────────────────────────────────────────────────────┘
```

Интерфейсы объявляются **на стороне потребителя** (в пакете `service`), а не в пакете
репозитория — это идиоматично для Go и не даёт репозиторию диктовать контракт.

```go
// internal/service/link.go
type LinkRepository interface {
    Create(ctx context.Context, l Link) (Link, error)
    GetByCode(ctx context.Context, code string) (Link, error)
    GetByURL(ctx context.Context, url string) (Link, error) // для идемпотентности
    IncrementClicks(ctx context.Context, code string) error // Этап 1
    Delete(ctx context.Context, code string) error
}

type Cache interface {
    Get(ctx context.Context, code string) (Link, bool, error)
    Set(ctx context.Context, l Link, ttl time.Duration) error
    Del(ctx context.Context, code string) error
}
```

## Поток создания ссылки

Одинаков для обоих этапов.

```
POST /api/v1/links {url, custom_alias?, ttl_seconds?}
        │
   handler: декод JSON, валидация (url не пуст, схема http/https,
            алиас по [a-zA-Z0-9_-]{3,32}, ttl_seconds >= 0)
        │
   service:
     1. нормализовать URL
     2. если custom_alias задан → code = alias, is_custom = true
        иначе → сгенерировать code (base62 от счётчика/хэша)
     3. вычислить expires_at = now + ttl (если ttl задан)
     4. repo.Create(...)  ── полагается на UNIQUE-констрейнты:
          - PK(code)          → коллизия алиаса = ErrAliasTaken (409)
          - UNIQUE(url_hash)  → идемпотентность: тот же URL → тот же код
        │
   repo: INSERT ... ON CONFLICT (url_hash) DO NOTHING RETURNING ...
         если строки нет → SELECT существующей (тот же код)
        │
   handler: 201 Created {code, short_url, expires_at}
            (или 200, если вернулась существующая — см. api.md)
```

Идемпотентность реализуется на уровне БД через `UNIQUE` по хэшу URL — это единственный
надёжный способ при гонке двух одновременных вставок одного URL. Подробности в
[data-model.md](./data-model.md).

## Поток редиректа — Этап 1 (синхронный)

Счётчик инкрементится **на горячем пути, блокируя ответ**. Это намеренно.

```
GET /{code}
   │
   ├─▶ Redis GET code ──── hit ──┐
   │        miss                 │
   │         │                   │
   │   Postgres SELECT by code   │
   │         │                   │
   │   not found → 404           │
   │         │                   │
   │   Redis SET code (populate) │
   │         ▼                   │
   ├──────── проверка expires_at ◀┘
   │         │ просрочена → 410 Gone
   │         ▼
   │   Postgres UPDATE click_count = click_count + 1   ◀── СИНХРОННО, БЛОКИРУЕТ
   │         │
   │         ▼
   └─▶ 302 Found, Location: original_url
```

Узкое место: каждый редирект ждёт `UPDATE` в Postgres. Под нагрузкой p99 редиректа
тащит за собой латентность записи в БД и контеншн по строке счётчика. Именно это
мы измеряем и потом убираем.

## Поток редиректа — Этап 2 (асинхронный)

```
GET /{code}
   │
   ├─▶ Redis GET code ── hit ──┐
   │        miss               │
   │   Postgres SELECT         │
   │   Redis SET (populate)    │
   │         ▼                 │
   ├──────── проверка TTL ◀─────┘
   │         │ просрочена → 410
   │         ▼
   │   clickCh <- ClickEvent{code, ts}   ◀── НЕ блокирует (буфер + drop-политика)
   │         │  (если буфер полон → drop + метрика, ответ не задерживаем)
   │         ▼
   └─▶ 302 Found, Location: original_url   ◀── отвечаем СРАЗУ
```

Ответ больше не зависит от записи в БД. Запись делает воркер-пул асинхронно. Это и есть
рефакторинг, ради которого затевался проект.

## Async click pipeline

Сердце Этапа 2. Один буферизованный канал → пул воркеров → батчевый флаш.

```
   redirect handlers (N горутин)
        │  clickCh <- event   (неблокирующий send, см. backpressure)
        ▼
 ┌────────────────────────────┐
 │  clickCh: chan ClickEvent  │  буфер = CLICK_CHANNEL_BUFFER (напр. 10000)
 └──────────────┬─────────────┘
                │ range clickCh
   ┌────────────┼────────────┬────────────┐
   ▼            ▼            ▼            ▼
 worker0      worker1      worker2     workerK     (WORKER_POOL_SIZE воркеров)
   │
   │  каждый воркер накапливает локальный батч map[code]int
   │  flush когда:  len(batch) >= BATCH_SIZE_N    (по размеру)
   │            ИЛИ  сработал time.Ticker(FLUSH_INTERVAL_T)  (по времени)
   │            ИЛИ  канал закрыт (drain на shutdown)
   ▼
 Postgres: один UPDATE ... FROM (VALUES ...) — агрегированный апдейт
           click_count += delta для всех кодов батча за один запрос
   │
   └─▶ (опционально) Kafka producer: каждое событие → topic clicks (fire-and-forget)
```

Ключевые свойства:

- **Агрегация в батче по `code`.** Если один код кликнули 50 раз за окно, это `+50` одним
  обновлением строки, а не 50 апдейтов. Резко снижает контеншн и число round-trip.
- **Два триггера флаша.** Размер `N` ловит всплески трафика, таймер `T` гарантирует, что
  при низком трафике счётчики не «зависают» надолго невидимыми. Что наступит раньше.
- **Идемпотентность не нужна** — это инкремент-дельты, не set. Но при сбое флаша батч можно
  потерять; для учебного счётчика это допустимо (см. backpressure и Kafka).

Псевдокод воркера:

```go
func (w *worker) run(ctx context.Context) {
    batch := make(map[string]int, cfg.BatchSize)
    ticker := time.NewTicker(cfg.FlushInterval)
    defer ticker.Stop()

    flush := func() {
        if len(batch) == 0 {
            return
        }
        if err := w.repo.BatchIncrement(ctx, batch); err != nil {
            w.metrics.FlushErrors.Inc()
            // лог + при желании retry; батч уже агрегирован
        }
        w.metrics.BatchSize.Observe(float64(len(batch)))
        batch = make(map[string]int, cfg.BatchSize)
    }

    for {
        select {
        case ev, ok := <-w.ch:
            if !ok {           // канал закрыт → финальный drain
                flush()
                return
            }
            batch[ev.Code]++
            if len(batch) >= cfg.BatchSize {
                flush()
            }
        case <-ticker.C:
            flush()
        case <-ctx.Done():     // принудительная отмена: дренируем что есть и выходим
            flush()
            return
        }
    }
}
```

## Анализ backpressure

Когда `clickCh` полон, у send есть три стратегии. Send выполняется в обработчике
редиректа — на **горячем пути**, и его поведение определяет латентность.

| Стратегия | Поведение при полном канале | Плюсы | Минусы |
|---|---|---|---|
| **Блокирующий send** (`ch <- ev`) | редирект ждёт, пока освободится место | ни одного потерянного клика | возвращает блокировку на горячий путь — ровно та боль, которую мы убирали; p99 деградирует, риск каскада |
| **Неблокирующий drop** (`select { case ch <- ev: default: drop }`) | клик отбрасывается, инкремент метрики `clicks_dropped_total` | редирект всегда мгновенный, латентность защищена | при перегрузке часть кликов недосчитана |
| **Drop oldest** | вытеснить старое событие | ограниченное отставание | сложнее, тот же риск потери |

### Рекомендация: неблокирующий drop + метрика

Для счётчика кликов **точность не критична**, а **латентность редиректа — это весь смысл
проекта**. Поэтому:

```go
select {
case s.clickCh <- ev:
    // ушло в конвейер
default:
    s.metrics.ClicksDropped.Inc() // backpressure виден в Prometheus
}
```

Обоснование:
- Горячий путь никогда не блокируется — p99 редиректа остаётся плоским даже при перегрузке.
- Дропы **наблюдаемы**: метрика `clicks_dropped_total` показывает, что система на пределе,
  и это сигнал поднять `WORKER_POOL_SIZE`/`CLICK_CHANNEL_BUFFER` или ускорить флаш.
- Буфер `CLICK_CHANNEL_BUFFER` подобран так, чтобы дропы случались только в реальной
  перегрузке, а не в нормальном всплеске.

Точную аналитику (если нужна без потерь) ведёт **Kafka-конвейер** с at-least-once — счётчик
в `links` остаётся «достаточно точным» оперативным числом, а Kafka — источником правды для
расширенной статистики (`/api/v1/links/{code}/stats`).

## Graceful shutdown и drain

Цель: по сигналу (`SIGINT`/`SIGTERM`) **не потерять ни одного события, уже принятого в канал**.

Последовательность (точный порядок важен):

```
1. Получen SIGINT/SIGTERM (signal.NotifyContext).
2. http.Server.Shutdown(ctxTimeout):
     - перестаём принимать новые соединения,
     - даём текущим запросам доиграть (они либо уже сделали send, либо не сделают).
3. close(clickCh):
     - после Shutdown новых send в канал не будет → закрывать безопасно.
4. workerPool.Wait():
     - воркеры дочитывают range по каналу до конца,
     - на закрытии канала делают финальный flush() остатка батча,
     - sync.WaitGroup ждёт завершения всех воркеров.
5. Останавливаем expiry sweeper (отмена его ctx) и Kafka producer (flush + close).
6. Закрываем pgxpool и redis client.
7. Выходим.
```

ASCII последовательности:

```
signal ──▶ http.Shutdown ──▶ close(clickCh) ──▶ workers drain & final flush ──▶ wg.Wait
                                                       │
                                              sweeper.Stop / kafka.Close
                                                       │
                                              pgxpool.Close / redis.Close ──▶ exit
```

Тонкость: **нельзя** `close(clickCh)` до `http.Shutdown` — иначе обработчик может сделать
send в закрытый канал и упасть с паникой. Порядок «сначала перестать принимать запросы,
потом закрыть канал» обязателен.

`ctx.Done()` в воркере (см. псевдокод) — это аварийный путь для случая, когда отведённый на
shutdown таймаут истёк: тогда дренируем текущий батch и выходим, даже если в канале ещё
что-то осталось. Нормальный путь — через `close(clickCh)` и дочитывание `range`.

## Kafka: семантика доставки

Каждое событие клика дополнительно уходит в топик `clicks` для внешней аналитики.
README просит «потрогать оба» подхода — fire-and-forget и at-least-once.

### Fire-and-forget (asynchronous, acks=1 / acks=0)

```go
// franz-go / segmentio: отправляем и не ждём подтверждения в горячем коде
producer.Produce(ctx, record, func(r *kgo.Record, err error) {
    if err != nil {
        metrics.KafkaProduceErrors.Inc() // только метрика, не блокируем
    }
})
```

| | |
|---|---|
| Латентность | минимальная, не на горячем пути |
| Гарантии | можно потерять событие при сбое брокера/буфера |
| Когда | счётчик кликов, оперативная аналитика «примерно» — допустима потеря |

### At-least-once (acks=all, idempotent producer, ретраи)

```go
cfg := []kgo.Opt{
    kgo.RequiredAcks(kgo.AllISRAcks()),
    kgo.ProducerBatchMaxBytes(...),
    kgo.RecordRetries(math.MaxInt), // ретраим до успеха
}
```

| | |
|---|---|
| Латентность | выше (ждём подтверждение всех реплик) |
| Гарантии | событие не теряется; возможны дубли → consumer должен быть идемпотентен |
| Когда | если `/{code}/stats` должна быть точной; дедуп по `(code, click_id)` на стороне consumer |

### Рекомендация

- **Счётчик в `links`** — питается из внутреннего канала с drop-политикой (быстро, «достаточно точно»).
- **Kafka-поток** — пускаем как отдельную ветку. Для учебной демонстрации: начать с
  **fire-and-forget** (проще, видно неблокирующую отправку), затем переключить конфигом на
  **at-least-once** и обсудить дубли/идемпотентность consumer'а. Producer тоже не должен
  сидеть на горячем пути: отправку делает либо воркер-пул, либо отдельная горутина, читающая
  из того же события.

> Решение (Kafka vs NATS): **Kafka**. Учебная ценность выше — партиции, consumer-группы,
> acks, idempotent producer, ретраи — это то, что спрашивают на собесах. NATS проще, но
> меньше «поверхности» для отработки семантики доставки. Если важна лёгкость локального
> поднятия — NATS JetStream допустимая замена, API конвейера от этого не меняется.

## Решение 301 vs 302

| | 301 Moved Permanently | 302 Found |
|---|---|---|
| Кэширование браузером | агрессивно кэшируется, часто навсегда | не кэшируется по умолчанию |
| Влияние на счётчик | браузер ходит мимо нас → **клики недосчитываются** | каждый клик доходит до сервиса |
| Гибкость | сложно «перецелить» ссылку | можно менять назначение |

**Рекомендация: 302 Found.** Для сокращателя со статистикой кликов 301 ломает учёт —
браузер закэширует и перестанет обращаться к сервису, счётчик замрёт. 302 гарантирует, что
каждый клик проходит через наш редирект и попадает в конвейер. Минус — нет браузерного кэша,
но для учебного сервиса с акцентом на метрики кликов это правильный компромисс.
